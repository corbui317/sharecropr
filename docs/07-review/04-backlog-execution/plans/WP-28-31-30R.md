## 0. Findings the plan depends on (checked in the code)

1. **No sign-out call site catches errors.** `auth-service.ts:98-104` `signOut()` rethrows on purpose; a test pins this (`auth-service.test.ts`, "wipes the query cache even if sign-out rejects"). All five `void signOut().then(() => router.replace(…))` calls therefore leave an unhandled rejection: the button does nothing and the user gets no feedback. The sites:
   - `DeletionStatusError.tsx:18`
   - `RestoreAccountScreen.tsx:37` and `:77`
   - `VerifyEmailScreen.tsx:75`
   - `app/(tabs)/profile/index.tsx:22`. Its logic sits under `app/`, so it cannot have a test in place (WP-AUTH-FIX constraint).
2. **`Retry-After` can be read without touching the database.** `AuthError` carries no headers. But supabase-js passes `global.fetch` to the auth client (`node_modules/@supabase/supabase-js/dist/index.cjs:645`, `_initSupabaseAuthClient(..., settings.global.fetch)`). A fetch wrapper in `src/api` can read `Retry-After` from 429 responses on `/auth/v1/*`. This is a fetch wrapper only: no React Native imports, which satisfies Invariant 11.
   - Fallback: when GoTrue refuses a resend inside `max_frequency`, its error message reads "you can only request this after N seconds", so N can be parsed from the message.
   - Whether hosted GoTrue sends `Retry-After` on sign-in (IP limit) is unverified. The interim copy stays as the fallback.
3. **R29: a rate-limit message on password reset would reveal whether the account exists.**
   - GoTrue's per-user `max_frequency` (`config.toml:80`, "1m") returns 429 only for addresses that have an account.
   - An SMTP 500 likewise happens only for an existing user.
   - So ForgotPassword may show distinct copy only for a true transport failure (status 0). Every other result must show the standard success screen.
   - §8.2's "Rate limited" row currently lists reset among the countdown cases. It must be amended (Q3).
4. **Email verification is broken on a device.** `signUpWithEmail` (`auth-service.ts:69-72`) and `resendVerificationEmail` (`:107-110`) pass no `emailRedirectTo`, so GoTrue falls back to `site_url = http://127.0.0.1:3000` (`config.toml:40`). `sharecropr://auth/callback` is already allowlisted (`config.toml:45`) and no route exists for it, so **WP-30's client fix needs no `supabase/**` edit.**
5. **The OAuth redirect shares that URL.** `oauth.ts:10-13` uses `sharecropr://auth/callback`. On Android the Custom Tab redirect can also reach Expo Router. A new callback route that exchanges `?code=` would race `oauth.ts:97`'s exchange, and the PKCE verifier is single-use. Both callers must therefore go through one single-flight exchange per code, the pattern `exchangeRecoveryCode` already uses (`auth-service.ts:126-143`).
6. **A failed PKCE exchange cannot be retried.** auth-js removes the verifier even when the network fails (`GoTrueClient.js:1621-1650`, `removePKCEVerifier` in both the success path and the `catch`), so "retry the exchange" does not work. For a signup link, GoTrue has already confirmed the email before it redirects. The honest failure state is therefore §8.3 "This link was already used. Try signing in."
7. **GoTrue often puts error params in the URL fragment.** For an expired token it cannot tell which flow type the link belongs to, so it falls back to `#error=…&error_code=otp_expired`. `useLocalSearchParams` does not read fragments. `ResetPasswordScreen.tsx:17-20,48` reads only the query string, so a **signed-in** user who opens an expired reset link gets the new-password form (`link = session ? 'ready'`). That is also an R32 hole (WP-33).
8. **The resend cooldown is 3600 s after a single successful resend** (`VerifyEmailScreen.tsx:13,37,47`). Server config is a 60 s minimum interval (`config.toml:80`) and R18 allows 3 per hour.
9. **Spinners that never end (Invariant 10).** `ForgotPasswordScreen.tsx:16-21` has no try/finally, so a rejected call leaves `loading` true forever. `SignInScreen.tsx:29-31` and `VerifyEmailScreen.tsx:31-34` have the same problem if the SDK throws a non-AuthError.
