```sql
-- SCR-0201: the break_glass role (RLS Design §2, Location Privacy §10, Runbooks §6).
--
-- This migration creates the role only: NOLOGIN, NOINHERIT, no attributes, no grants,
-- no memberships. It deliberately does NOT grant SELECT on private.garden_locations.
-- That grant, the 60-minute time box, two-person activation and per-statement audit
-- belong to the break-glass provisioning script (`npm run ops:break-glass`, Runbooks §6),
-- which does not exist yet. Until it does, the role can do nothing.
--
-- Roles are cluster-wide and survive a database re-create, so creation is guarded.
-- Asserted by supabase/tests/roles_break_glass.test.sql.

DO $$
BEGIN
  IF NOT EXISTS (SELECT 1 FROM pg_catalog.pg_roles WHERE rolname = 'break_glass') THEN
    CREATE ROLE break_glass
      NOLOGIN NOINHERIT NOSUPERUSER NOCREATEDB NOCREATEROLE NOREPLICATION NOBYPASSRLS;
  END IF;
END
$$;

COMMENT ON ROLE break_glass IS
  'Two-person authorized, time-boxed read of private.garden_locations (RLS Design §2). '
  'Holds no privileges until the provisioning script grants them for one ticket. Never grant in a migration.';
```

Why guarded: roles are cluster-level; a `db reset` that re-creates the database but not the cluster would otherwise fail with "role already exists". Re-applying the file was tested (idempotent).

## 5. Convention doc — Data Model §15 (AC2)

File `docs/01-architecture/03-data-model.md`. Header `**Version:** 1.3.0` → `1.4.0`. Replace the whole §15 body (rules 1–6 are kept verbatim in substance, 1 is expanded, 7–11 are new) with:

```markdown
## 15. Migration rules

Migrations live in `supabase/migrations/` and are applied in filename order by the Supabase CLI (`supabase db reset` locally and in CI).

1. **Forward-only.** No `DOWN` migrations, and no edits to a migration once it is on `develop`. A mistake is fixed by a new corrective migration, not by rewinding a database ([CI/CD §8](../05-operations/02-cicd.md#8-rollback), [ADR-0004](adr/ADR-0004-supabase.md); confirmed for SCR-0007 under SCRUM-18). A bad contract migration is recovered by point-in-time restore, which is why contract phases are gated.
2. **Expand → migrate → contract.** Add the new column, dual-write, backfill, switch reads, then drop — across at least two releases.
3. **A destructive migration (`DROP`, `ALTER TYPE`, `NOT NULL` on an existing column) fails CI** if more than 2% of DAU are on an app version predating the contract phase. Enforced mechanically from `devices.app_version`.
4. **Every migration that creates a table must, in the same file,** enable RLS, create policies, and be accompanied by pgTAP tests in the same PR. CI rejects a new table with `rowsecurity = false`.
5. **No migration may `GRANT` on `private`.** CI greps for it and fails.
6. Migrations run against a production-shaped seed in CI before they can merge.
7. **File name: `<version>_<snake_case_name>.sql`, where `<version>` is exactly 14 digits, `YYYYMMDDHHMMSS` in UTC** — what `supabase migration new <name>` produces. The CLI takes everything before the first `_` as the version and records it as the primary key of `supabase_migrations.schema_migrations`, so two files with the same leading digits make `supabase db reset` fail. Versions are unique and strictly increasing; never reuse or renumber one. Check: `ls supabase/migrations | sed 's/_.*//' | sort | uniq -d` prints nothing and every prefix matches `^[0-9]{14}$`.
8. **Refer to a migration by its full file name.** The ten pre-convention files were renamed on 2026-10-21 (SCR-0201) from `YYYYMMDD_NNNN_name.sql` to `YYYYMMDD00NNNN_name.sql`; their `HHMMSS` is the old ordinal, not a time, so short references such as "0004" in their comments still resolve. Names like `0003_mfa.sql` in specs are placeholders: the real file gets a version when it is written.
9. **One concern per file.** A migration does one reviewable thing (a table with its RLS and policies, a function family, a role). Unrelated fixes go in separate files so each can be reviewed and, if needed, corrected forward on its own.
10. **Its test ships in the same PR.** Every migration that changes behaviour or privileges lands with the pgTAP file that asserts it (`supabase/tests/*.test.sql`), with negative assertions outnumbering positive ones (NFR-47).
11. **Roles are created idempotently and with no privileges.** Roles are cluster-wide, so `CREATE ROLE` is guarded by a `pg_roles` check. A new role starts `NOLOGIN` with no grants; privileges are granted explicitly, in a reviewed migration or (for `break_glass`) only by the provisioning procedure ([Runbooks §6](../05-operations/05-runbooks.md)).
```
