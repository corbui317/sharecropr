## Planner findings (read before starting)

1. **display_point is stable per garden, by design.** Location Privacy §4.1 says "Deterministic per garden. Defeats the averaging attack." `app.derive_display_point(exact, fuzz_seed)` in `20260822_0003_gardens_geospatial.sql` is `IMMUTABLE` and derives distance and bearing from `sha256(fuzz_seed)`. `fuzz_seed` is fixed per row in `private.garden_locations`. The trigger `private.sync_garden_derived_location` writes `gardens.display_point` once per change to `exact_point`. Every client read therefore returns the same stored value. So LP-06 asserts two things: (a) the mean of 1,000 client reads is more than 400 m from `exact_point` (the spec's LP-06 wording), and (b) that mean equals the stored `display_point`, meaning there is no per-read noise that would converge on the true point. This matches the queue's risk note.
2. **Why the repo test fails today:** `MIN(truth)` on geography raises `ERROR: function min(geography) does not exist` at line 47. pg_prove then stops after 4 of 13 tests (harness BASELINE.md). `CROSS JOIN generate_series(1,100)` also copies one stored row 100 times, so even with the error fixed the test would only repeat LP-04.
3. **The client path:** `gardens_select_own` (0004) lets `authenticated` read its own row, and 0010 grants column `SELECT (… display_point …)` to `authenticated`. No policy lets one user read another user's garden yet, so the owner reading their own garden is the only client path that exists. `private.garden_locations` is unreadable as `authenticated`, so the test takes its samples as `owner` into a temp table, calls `tests.clear_authentication()`, and then compares as `postgres` (BYPASSRLS, the same role LP-04 uses to read `private`). Granting `INSERT` on a session temp table to `authenticated` works. The harness confirmed it.
4. **Negative-ratio gate (`scripts/ci-assert-negative-ratio.sh`).** It counts lines with grep. Positives match `'P[0-9]+:`. Negatives match `'N[0-9]+:|'LP-[0-9]+:|'LP:`. It does not parse pass() or skip() at all, only the quoted description prefix. The four `pass('LP-08: …')` lines currently count as negatives, which inflates them. Each new `skip()` description starts with `'SCR-…` and has no `'LP-NN:`, so they drop out of the count (SCRUM-44 AC2: "excluded from the negative count"). The three new LP-06 assertions all start with `'LP-06:` and count. Measured: **before `P=0 N=12`, after `P=0 N=10`**, gate exit 0, every other file unchanged.
5. **Backlog keys for the skips** come from `docs/06-roadmap/03-delivery-backlog.md`:
   - LP-08 (telemetry scrubber, Sentry) → **SCR-1701** "Sentry wired … PII scrubbing verified against NFR-45" (EPIC-17)
   - LP-09 (EXIF) → **SCR-0604** "media-process strips EXIF … before the asset is readable" (EPIC-06)
   - LP-10 (production canary) → **SCR-0210** (EPIC-02)
   - LP-12 (cell-boundary recall for safe spots) → **SCR-0804** `rpc.safe_spots_near` (EPIC-08). The old text said "EPIC-07", which is Crop Taxonomy. Safe Spots is EPIC-08, so the new text corrects it.
   These mappings are a judgement call, not one of the open decisions. The integrator should mention them on SCRUM-44.
6. **Invariant 1:** every new assertion is `ok()` on a boolean or `is()` on an integer count. On failure, pgTAP prints only the description, `(test result was NULL)`, or `have: 0 / want: 1000`. The harness confirmed this: on mutated runs it found no WKB/`POINT` or float coordinates in `.tap` or `.err`. Do not change these to `is()`, `cmp_ok()` or `results_eq()` on geography or distance values.
7. Out of scope, noted for the report only: **LP-05 has the same vacuity as old LP-06** (`FROM gardens g, generate_series(1,100)` reads one row once and repeats it). LP-04/05/07 at spec sizes (10,000 gardens, 1,000 reads, χ²) belong to **WP-19** (queue `remaining_after`). Do not fix them here.

```sql
-- LP-06: averaging resistance (Location Privacy §11; mean of 1,000 reads > 400 m from truth).
-- display_point is deterministic per garden (§4.1), so the attack is: read the same garden
-- 1,000 times through the client path and average. Each read is a separate execution of the
-- PostgREST-shaped query, as `authenticated` with JWT claims, under RLS (gardens_select_own).
-- Exact coordinates never leave SQL: assertions use ok()/is() on booleans and counts only.
CREATE TEMP TABLE lp06_samples (p geography(Point, 4326)) ON COMMIT DROP;
GRANT INSERT ON lp06_samples TO authenticated;
SELECT tests.authenticate_as('owner');
DO $$
BEGIN
  FOR i IN 1..1000 LOOP
    INSERT INTO lp06_samples (p)
    SELECT g.display_point FROM public.gardens g WHERE g.id = tests.fixture('owner_garden');
  END LOOP;
END $$;
SELECT tests.clear_authentication();

SELECT is(
  (SELECT count(p) FROM lp06_samples)::int,
  1000, 'LP-06: 1000 client-path reads each returned a display_point');

SELECT ok(
  (SELECT ST_Distance(
            ST_Centroid(ST_Collect(s.p::geometry))::geography,
            (SELECT l.exact_point FROM private.garden_locations l
              WHERE l.garden_id = tests.fixture('owner_garden'))) > 400
     FROM lp06_samples s),
  'LP-06: mean of 1000 client reads stays >400m from exact_point');

SELECT ok(
  (SELECT ST_Distance(
            ST_Centroid(ST_Collect(s.p::geometry))::geography,
            (SELECT g.display_point FROM public.gardens g
              WHERE g.id = tests.fixture('owner_garden'))) < 0.01
     FROM lp06_samples s),
  'LP-06: mean of client reads equals the stored display_point (no per-read noise)');

```
